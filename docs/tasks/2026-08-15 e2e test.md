# Infinite Canvas — E2E 테스트 환경 점검 및 커버리지 테스트 작성

작성일: 2026-08-15
상태: WSL→Windows Chrome 자동화 인프라는 시도 후 롤백, 의미 있는 e2e 커버리지 테스트 작성 완료

## 요구사항

처음 요청은 "회사의 테스트 환경을 여기(WSL)에도 구축 — Windows Chrome 브라우저로 Playwright e2e
테스트를 실행"이었다. 작업 도중 회사 환경과의 모순이 드러나면서 요구사항이 재정의됐고, 최종적으로는
"회사 설정 파일은 그대로 두고, 캔버스 핵심 기능을 실제로 검증하는 의미 있는 e2e 테스트 케이스를
작성"으로 마무리됐다. 아래 두 절이 그 순서를 그대로 따른다.

## 시도 1 — WSL에서 실제 Windows Chrome을 CDP로 구동 (롤백됨)

- **문제 재현**: WSL 안에서 `chromium.launch({ executablePath: '.../chrome.exe' })`로 Windows
  Chrome을 직접 띄우면, Playwright의 기본 CDP 통신 방식(pipe transport)이 WSL↔Windows 프로세스
  경계를 넘지 못해 `Remote debugging pipe file descriptors are not open` 에러로 즉시 죽는 것을 직접
  재현해 확인했다.
- **우회책 구현**: `chrome.exe`를 `--remote-debugging-port`로 별도 스폰한 뒤
  `chromium.connectOverCDP()`로 연결하는 방식을 `e2e/global-setup.ts`(포트 대기 + CDP 준비 확인),
  `e2e/global-teardown.ts`(PowerShell로 프로필 태그 매칭해 프로세스 트리 종료), `e2e/fixtures.ts`
  (`browser` 픽스처를 오버라이드, CDP 대상이 없으면 기본 Playwright 브라우저로 자동 폴백)로
  구성했다. WSL이 아니거나 Windows Chrome이 없는 환경에서는 아무 영향이 없도록 설계했었다.
- **부수적으로 발견/조치한 문제**:
  - `playwright install`이 기본으로 안 쓰는 firefox/webkit까지 받아 느려짐 → `playwright install
    chromium`으로 좁힘.
  - Playwright가 자신이 띄운 `preview` 웹서버를 테스트 후 종료시키며 재확인하는 과정에서, WSL2
    네트워크 스택이 가끔 SYN 패킷을 블랙홀시켜(`SYN-SENT` 상태로 멈춤) 리눅스 커널 TCP 타임아웃(약
    2~3분)을 그대로 소모하는 현상을 로그 타임스탬프로 특정했다. `webServer.reuseExistingServer:
    true`로 우회.
  - 디버깅 중 20분 넘게 떠 있던 사용자의 기존 `vite dev` 프로세스를 실수로 종료시켜, 즉시 알리고
    재기동 방법을 안내했다.
- **롤백 경위**: "회사에서는 이런 설정 파일 없이도(WSL+Windows Chrome인데도) 잘 됐다"는 사용자의
  문제 제기로 시작해, 회사 환경도 이 세션과 동일한 조합(WSL + Windows Chrome)이라는 게 확인되면서
  모순이 드러났다. 이 리포지토리가 회사 repo와 완전히 동일하다는 것도 함께 확인되면서 — 즉 "회사가
  이미 구성해 둔 것을 가져다 쓴 것"일 가능성도 배제됨 — 결국 "회사에서 본 것은 e2e 테스트 자동화가
  아니라 AI 에이전트가 그때그때 임의로 브라우저를 조작(CDP로 스크린샷을 찍어 보여주는 등)한
  결과였을 것"으로 정리됐다. 사용자가 `playwright.config.ts`, `package.json`(`test:e2e` 스크립트),
  `README.md`, `.gitignore`, 데모 e2e 테스트 파일의 import를 전부 원래 상태로 직접 되돌리고, 이
  세션이 만든 `e2e/`(global-setup/teardown/fixtures) 디렉터리를 삭제했다. 즉 **브라우저 자동화
  인프라 자체는 이번 작업의 목적이 아니었다** — 최종 상태의 `git status`는 완전히 클린하다(추가
  파일 없음).

## 시도 2 (최종 결과물) — 의미 있는 e2e 커버리지 테스트 작성

- **확인된 사실**: 유일하게 존재하던 e2e 테스트(`src/routes/demo/playwright/page.svelte.e2e.ts`)는
  `git log --follow`로 확인한 결과 최초 커밋(`81b2129 Initial release`)부터 한 번도 바뀐 적 없는
  SvelteKit 스캐폴딩 placeholder였다 — `/demo/playwright` 페이지의 `<h1>Playwright e2e test
  demo</h1>` 하나가 보이는지만 확인하고, 캔버스 핵심 기능은 전혀 검증하지 않고 있었다. 브라우저가
  뜨자마자 닫히는 것처럼 보인 것도 이 테스트 자체가 원래 아무것도 안 하기 때문이었다.
- **신규 작성**: `src/routes/page.svelte.e2e.ts` — 실제 앱(`/`)을 대상으로 한 9개 테스트.
  회사 설정 파일(`playwright.config.ts`, `package.json` 등)은 전혀 건드리지 않고 테스트 파일 하나만
  추가했다.
  1. 초기 로드 시 기본 문서("Canvas")와 기본 레이어("레이어 1")가 준비되는지
  2. 펜으로 실제로 마우스 스트로크를 그어 캔버스 픽셀이 흰 배경(`#ffffff`)에서 전경색(`#1a1a1a`)
     으로 바뀌는지 — `getImageData`로 픽셀 단위 검증
  3. 지우개로 칠한 자리를 지우면 배경색으로 복원되는지
  4. 단축키 `E`로 펜⇄지우개가 토글되는지
  5. 레이어를 추가하면 목록에 "레이어 2"가 생기고 곧바로 활성 레이어가 되는지
  6. 레이어 투명도 슬라이더 값이 표시 퍼센트에 즉시 반영되는지
  7. 컬러 피커에서 hex를 입력하면 툴바 스와치뿐 아니라 실제로 캔버스에 그려지는 색까지 바뀌는지
  8. `Ctrl+S` 수동 저장 시 저장 상태 인디케이터가 뜨는지
  9. 그림을 그리고 저장한 뒤 `page.reload()`해도 픽셀이 그대로 남아있는지 — 이 앱의 "서버 없이
     브라우저에만 저장" 핵심 설계를 직접 검증
- **픽셀 검증 시 주의점**: `renderer.ts`가 매 프레임 배경색을 불투명하게 먼저 채우고 그 위에
  레이어를 합성하기 때문에, 최종 캔버스는 항상 알파 255다. 따라서 "칠해졌는지/지워졌는지"는 알파가
  아니라 RGB 값으로 판단해야 한다는 걸 렌더러 소스를 직접 읽어 확인하고 테스트에 반영했다.

## 검증

- 회사 설정을 전혀 수정하지 않은 상태에서 `npx playwright test src/routes/page.svelte.e2e.ts` 실행,
  9개 전부 통과(개별 130ms~482ms). 기존 데모 placeholder 테스트는 그대로 남겨뒀다.

## 알려진 한계 (의도적으로 남겨둠)

- 태블릿 필압, 패닝/줌 제스처, 배경 텍스처 업로드, 문서 전환/이름변경/삭제, 서버로 내보내기(export)
  등은 이번 스코프에 포함하지 않았다 — 요청 범위가 "의미 있는 커버리지"였지 "전체 기능 커버리지"가
  아니었다고 판단했다. 필요하면 같은 패턴(픽셀 샘플링 + aria-label 기반 셀렉터)으로 이어서 작성할 수
  있다.
- 이번에 회사 환경이 실제로 어떻게 Playwright를 구동하는지는 끝내 명확히 확인되지 않았다 — 이
  문서의 "시도 1" 절이 그 조사 과정과, 결론이 "브라우저 자동화 인프라가 아니라 AI 에이전트의 즉석
  조작이었을 것"으로 정리된 경위를 기록해 둔다.
