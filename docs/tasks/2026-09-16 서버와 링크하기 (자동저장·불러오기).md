# 서버와 링크하기 (자동저장 · 불러오기 · 논블로킹 스냅샷)

작성일: 2026-09-16
상태: 구현 완료, 자동 검증 + 브라우저 수동(Playwright/CDP) 검증 완료

## 요구사항

기존에는 툴바에 "서버로 내보내기" 팝오버가 있어, 사용자가 URL을 입력하고 "보내기"를 누르면 그
순간의 `.infcanvas` 컨테이너를 그 URL에 한 번 `POST`하는 일회성 기능이었다. 이를 다음으로
바꾼다:

1. "서버와 링크하기" 버튼으로 교체 — 아이콘도 링크 아이콘으로.
2. 링크되면 자동저장(10분 간격)과 불러오기가 가능해진다.
3. 링크된 상태에서 링크를 해제할 방법(버튼)을 마련한다.
4. 자동저장 중에도 드로잉 동작이 블록되지 않도록 캔버스 스냅샷 기능을 추가한다.

## 조사

기존 로컬 자동저장(`persistence.ts`의 `saveDocument`/`startAutosaveLoop`, 30초 간격, OPFS
대상)은 이미 dirty 타일만 Dexie에서 읽어 재인코딩하는 구조라 "그리기를 막지 않는다"는
조건은 웬만큼 충족하고 있었다. 하지만 자세히 보면 두 가지 지점에서 개별 Dexie 오퍼레이션을
순차 실행할 뿐 하나의 트랜잭션으로 묶여 있지 않았다:

- dirty 타일 목록을 읽는 시점과, 재인코딩이 끝난 뒤 그 타일들의 `dirty`를 `false`로 지우는
  시점 사이에 시간차가 있다. 그 사이에 사용자가 같은 타일에 새 스트로크를 그리면(각 스트로크의
  `flushTouchedTiles`가 그 타일을 다시 `dirty:true`로 쓴다), 저장 루틴 끝에서 "저장 시작 시점에
  가져온" 오래된 타일 목록을 기준으로 무조건 `dirty:false`를 덮어써 버려 방금 그린 스트로크의
  dirty 플래그가 잘못 지워질 수 있었다.
- 서버 자동저장은 네트워크 왕복이 들어가 로컬 OPFS 쓰기보다 훨씬 오래 걸릴 수 있으므로, 이
  경쟁 조건의 실제 발생 가능성이 로컬 자동저장보다 훨씬 커진다.

IndexedDB 트랜잭션은 애초에 네트워크 요청처럼 다른 종류의 비동기 작업을 기다리는 동안에는 자동
커밋되어 버리므로, "느린 인코딩+PUT까지 통째로 하나의 Dexie 트랜잭션으로 묶기"는 불가능하다.
그래서 "dirty 상태를 읽고 지우는 것만 하나의 짧은 트랜잭션으로 원자적으로 끝내고, 그 트랜잭션
안에서 이미 복사해 둔 픽셀 버퍼만 가지고 트랜잭션 밖에서 인코딩·전송을 진행"하는 스냅샷
패턴으로 해결했다 — 이게 요구사항의 "캔버스 스냅샷 기능"이다.

## 변경 사항

### web (클라이언트)

- **`src/lib/canvas/containerSnapshot.ts`(신규)** — `buildContainerSnapshot(documentId)`.
  `db.transaction('rw', documents, layers, tiles, tilePixels, textures, ...)` 안에서 dirty
  타일 목록을 읽고 그 자리에서 바로 `dirty:false`로 지운 뒤(Dexie/IndexedDB가 같은 테이블에
  걸친 두 rw 트랜잭션을 항상 직렬화해 주므로, 이 트랜잭션과 브러시 스트로크의
  `flushTouchedTiles` 트랜잭션은 절대 서로의 쓰기를 반쯤 덮어쓰지 않는다), 트랜잭션 밖에서
  `webpWorkerPool`로 인코딩해 컨테이너를 만든다. 기존 `persistence.ts`의 자동저장 캐시
  공유(`tilePixels.webpCache`에 인코딩 결과를 다시 써넣는 것)와 달리, 이 경로는 그 캐시에
  쓰지 않는다 — 인코딩이 트랜잭션 밖(느림)에서 끝나는 시점에 그사이 타일이 또 바뀌었을 수 있어,
  캐시에 쓰면 "지금 픽셀과 안 맞는 캐시"를 남기는 새로운 경쟁을 만들 수 있기 때문이다.
- **`src/lib/canvas/serverLink.ts`(신규)** — `fetchRemoteContainer`/`syncDocumentToServer`(PUT)
  /`linkDocumentToServer`/`unlinkDocumentFromServer`/`loadDocumentFromServer`
  /`startServerAutosaveLoop`(10분, `persistence.ts`의 자기예약형 setTimeout 패턴 재사용).
  `linkDocumentToServer`는 그 URL에 이미 저장된 캔버스가 있으면 콜백으로 덮어쓰기 확인을 받고,
  거절하면 링크 자체를 성립시키지 않는다(거절을 "내 로컬로 원격을 덮어써라"로 확대 해석하지
  않음). 없으면 즉시 현재 로컬 상태를 PUT해 링크를 확립한다.
- **`src/lib/canvas/bootstrap.ts`** — 기존 `hydrateDocumentFromOpfs`의 몸통(unpack → Dexie
  반영 → 타일/텍스처 하이드레이션)을 `hydrateFromContainer`로 뽑아내고, 서버에서 받은 바이트를
  같은 경로로 반영하면서 그 결과를 OPFS 수동 저장 파일로도 즉시 쓰는
  `hydrateDocumentFromBytes`를 추가했다 — 그래야 다음 앱 시작 때도 OPFS(진실 공급원)와 어긋나지
  않는다.
- **`src/lib/canvas/document.svelte.ts`** — `linkedServerUrl` 상태와 `refreshLink()` 추가.
  **`reloadCurrentFromOpfs()`를 새로 추가**했다 — 처음엔 기존 `load(documentId)`를 재사용했는데,
  `load()`는 시작할 때 `loading = true`를 세팅하고 `+page.svelte`가 이걸로 Toolbar를 포함한
  전체 UI를 "불러오는 중…" 화면으로 통째로 바꿔버린다는 걸 브라우저 검증 중에 발견했다(아래
  "검증" 참고) — 서버에서 막 불러온 뒤 팝오버를 열어둔 채 상태 메시지를 보여주려 했는데, 팝오버를
  포함한 Toolbar 컴포넌트 자체가 통째로 언마운트/재마운트되면서 로컬 상태(`linkOpen`,
  `loadStatus`)가 다 날아가 버렸다. `reloadCurrentFromOpfs()`는 같은 하이드레이션을 하되
  `loading`을 건드리지 않는다.
- **`src/lib/canvas/types.ts` / `db.ts`** — `DocumentLinkRecord { documentId, serverUrl,
linkedAt }`와 `documentLinks` 테이블(버전 2) 추가. `.infcanvas` 컨테이너(manifest.json)에는
  넣지 않았다 — 어느 서버와 동기화할지는 파일 내용이 아니라 "이 브라우저의 로컬 설정"이라고
  판단했다(어느 폴더와 동기화할지가 파일 자체 내용이 아닌 것과 같은 이유).
- **`src/lib/components/Toolbar.svelte`** — `CloudUpload` 팝오버를 `Link`/`Unlink`(lucide)
  아이콘 기반 팝오버로 교체. 링크 안 된 상태엔 URL 입력 폼("링크하기"), 링크된 상태엔 현재 URL
  표시 + "불러오기" 버튼 + "연결 해제" 버튼을 보여준다. 링크 버튼 자체는 기존 도구 버튼과 같은
  `.active` 클래스로 링크 상태를 표시한다.
- **`src/routes/+page.svelte`** — `startServerAutosaveLoop`을 기존 로컬 자동저장 루프 옆에
  추가로 기동(문서가 링크되어 있을 때만 동작).
- **`src/lib/canvas/exportServer.ts`** — 일회성 서버 전송 함수(`exportDocumentToServer`) 제거,
  로컬 다운로드 기능만 남김.
- **`docs/api.md`** — PUT(저장, upsert)/GET(불러오기) 기반의 새 프로토콜로 전면 개정. 사용자가
  입력하는 URL 자체가 그 캔버스의 고유 리소스 주소가 된다(서버가 경로별로 구분해 저장하면 여러
  캔버스를 나눠 관리할 수 있음).

### server (참조 구현)

`web`의 새 프로토콜에 맞춰 함께 갱신해야 실제로 동작하므로 같이 손봤다:

- 기존 `POST /`(항상 새 타임스탬프 파일로 저장, 조회 불가)를 **경로별 upsert `PUT`/`GET`**으로
  전면 교체했다. `src/storage.ts`의 `pathToStorageKey`가 요청 경로(예: `/canvases/my-doc`)를
  안전한 파일명 하나로 매핑한다(경로 순회 방지를 위해 항상 평탄화, 서브디렉터리를 만들지 않음).
  자세한 내용은 `server/docs/tasks/`의 별도 보고서 참고.

## 검증

- **단위/통합 테스트**:
  - `web`: `containerSnapshot.svelte.spec.ts`(신규 3개) — 정상 스냅샷, 캐시 재사용, 그리고
    **인코딩이 진행되는 동안(트랜잭션이 끝난 뒤) 같은 타일에 새로 그려진 내용이 유실되지 않고
    다음 사이클을 위해 dirty로 남는지**를 `webpWorkerPool.encode`를 수동으로 지연시켜 직접
    검증. `serverLink.svelte.spec.ts`(신규 8개) — 링크(원격 없음/있음+승인/있음+거절),
    연결 해제, 수동 불러오기(원격 없음), 동기화 실패 처리, 자동저장 루프(dirty가 있을 때만
    PUT, 멈추면 더 안 함, 링크가 없으면 아무것도 안 함). 기존 `exportServer.svelte.spec.ts`에서
    제거된 함수를 테스트하던 케이스 2개 삭제. 전체 스위트 18개 파일 80개 테스트 통과,
    `svelte-check` 0 에러, lint(prettier+eslint) 통과.
  - `server`: 새 GET/PUT 라우트 테스트 통과(별도 보고서 참고).
- **브라우저 검증**(WSL→Windows Chrome, CDP 연결, `web` dev 서버는 사용자가 이미 실행 중이던
  `localhost:5173`을, `server`는 이번 작업을 위해 사용자가 직접 `localhost:3001`에 새로
  띄워줌): 실제 앱에서 Playwright로 전체 플로우를 확인했다.
  - 링크 안 된 상태에서 링크 버튼 클릭 → URL 입력 → "링크하기" → 서버에 아직 아무것도 없어(404)
    현재 로컬 상태를 즉시 PUT하고 링크됨(아이콘 active 상태로 전환, `aria-label`도 바뀜)을
    확인. 실제 브라우저의 cross-origin(5173→3001) `fetch` 왕복이라 CORS 프리플라이트까지
    실제로 통과해야 성공하는데, 정상 동작함을 확인.
  - 링크된 상태에서 팝오버를 다시 열면 저장된 URL, "불러오기" 버튼, "연결 해제" 버튼이 모두
    보임을 확인. 링크 상태에서도 캔버스에 실제로 스트로크를 그릴 수 있음을 확인(드로잉 회귀
    없음).
  - **"불러오기" 버튼을 눌렀을 때 처음엔 팝오버가 통째로 사라지는 버그를 실제로 발견**했다 —
    `documentState.load()`가 세팅하는 `loading` 플래그 때문에 Toolbar 전체가 언마운트되는
    것이었다. `reloadCurrentFromOpfs()`로 바꾼 뒤 재검증하니 팝오버가 열린 채로 "불러오는
    중…" → "완료" 상태가 정상적으로 보이고, 링크 상태도 유지됨을 확인했다.
  - "연결 해제" 클릭 시 링크 정보가 지워지고 버튼이 "서버와 링크하기"(미연결) 상태로 정확히
    되돌아가며, 팝오버를 다시 열면 URL 입력 폼이 다시 보임을 확인했다.
  - 검증에 쓴 테스트 도큐먼트 링크와 서버의 테스트 업로드 파일(`server/uploads/verify-*`)은
    작업 종료 시 정리했다. 다만 검증 중 실제로 캔버스에 그린 테스트 스트로크 하나는 이 앱에
    되돌리기(undo) 기능이 없어 지우지 못했다 — 사용자가 열어 둔 개발용 도큐먼트에 작은 대각선
    자국이 남아있을 수 있음.

## 알려진 한계 (의도적으로 남겨둠)

- 서버 링크는 "이 브라우저의 이 로컬 도큐먼트"에 종속된 설정이라(Dexie `documentLinks`
  테이블), `.infcanvas` 파일 자체를 다운로드해 다른 브라우저에서 열어도 링크 정보는 따라가지
  않는다 — 의도한 설계다(어느 서버와 동기화할지는 파일 내용이 아니라 로컬 설정).
- 자동저장 실패(네트워크 오류 등)는 `console.error`로만 남기고 UI에 별도 알림을 띄우지
  않는다 — 이 프로젝트에 토스트/알림 컴포넌트가 아직 없어서, 기존 로컬 자동저장 실패 처리와
  같은 수준으로 맞췄다.
- 링크된 서버가 다운되어 있거나 CORS를 잘못 설정한 경우 등은 "링크하기"/"불러오기" 버튼 클릭
  시점에만 사용자에게 드러난다(자동저장 실패는 조용히 다음 사이클을 기다림) — 반복 실패에 대한
  재시도/백오프 로직은 추가하지 않았다.
- 인증은 스펙 문서에 적힌 대로 URL 자체에 토큰을 심는 방식 등을 사용자가 직접 구성해야 한다
  (클라이언트/서버 어느 쪽도 별도 인증 로직을 갖지 않음).
