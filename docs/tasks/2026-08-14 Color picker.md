# Infinite Canvas — 컬러 피커 (Krita 컬러 휠로 교체)

작성일: 2026-08-14
상태: 구현 완료, 자동 검증 + 브라우저 수동(Playwright/CDP) 검증 완료

이 문서부터는 별도 마일스톤 번호를 붙이지 않고, 작업 단위로 날짜+주제 이름의 문서를 쓴다.

## 요구사항

기존 SV 사각형 + Hue 슬라이더 방식의 컬러 피커를, 사용자가 제공한 Krita 스크린샷의 "링(Hue) +
삼각형(Saturation/Value)" 컬러 휠로 교체한다. 세부 요구사항:

1. HSB 탭이 기본, RGB 탭으로 전환 가능
2. 현재 선택된 HSB/RGB 값이 탭 서브패널에 표시되고, 여기에 값을 입력하면 컬러 휠도 반응형으로 변한다
3. 오른쪽 컬러 팔레트를 컬러 히스토리 팔레트(사용한 색 목록)로 바꾼다. 단, 정확히 같은 색이 이미 있으면 중복 추가하지 않는다
4. 컬러 미리보기용 스크래치 패드(간단한 Canvas)를 우측 하단에 배치
5. 6자리 hex 값을 항상 표시하고, HSB/RGB 탭 패널 아래쪽에 그 이웃으로 둔다

## 구현 내용

- **`colorWheel.ts`(신규)** — 링+삼각형의 기하 계산과 캔버스 렌더링을 담당하는 순수 함수 모음.
  - 삼각형의 세 꼭짓점(순색/흰색/검은색)에 대한 무게중심좌표 `(u,v,w)`는 `u+v+w=1`을 만족하는
    아핀 파라미터인데, HSV의 정의(`V=u+v`, `S=u/(u+v)`, `u`=chroma)를 대입해 전개하면 "세 꼭짓점
    색을 무게중심좌표로 RGB 채널별 선형 보간"한 결과가 정확한 HSV 삼각형 그라디언트와 일치한다.
    그 덕분에 픽셀별 RGB 선형 블렌드만으로 채도/명도 그라디언트를 정확히 그릴 수 있어
    `drawSvTriangle`가 단순한 `ImageData` 루프로 끝난다.
  - Hue 링은 `CanvasRenderingContext2D.createConicGradient` + 두 원(바깥 시계방향, 안쪽 반시계방향)을
    `evenodd`가 아닌 기본 nonzero 규칙으로 클리핑해 도넛 모양을 만드는 방식으로 그린다(`drawHueRing`).
  - 삼각형 바깥을 드래그해도 항상 유효한 색이 나오도록, 클릭 지점을 삼각형 내부 최근접점으로
    클램프하는 `closestPointInTriangle`을 Ericson의 *Real-Time Collision Detection* 표준 알고리즘으로
    구현했다(꼭짓점/변/내부의 모든 보로노이 영역을 정확히 처리).
  - `hueToAngleRad`/`angleRadToHue`, `triangleVertices`, `svToBarycentric`/`barycentricToSv` 등은
    전부 캔버스나 DOM에 의존하지 않는 순수 함수라 `colorWheel.spec.ts`로 직접 단위 테스트했다
    (각도 왕복 변환, 무게중심좌표 왕복 변환, 클램프의 보로노이 영역별 동작 등 15개 케이스).
- **`ColorPicker.svelte`(전면 재작성)**:
  - 캔버스 두 장(`ring-canvas`, `triangle-canvas`)을 겹쳐서 휠을 그린다. 링은 마운트 시 한 번만
    그리고(정적), 삼각형은 `hsb.h`가 바뀔 때만 `$effect`로 다시 그린다(드래그 중 S/V만 바뀔 때는
    재렌더링하지 않아 가볍다). 두 개의 절대 위치 `div`가 각각 hue 선택 위치와 S/V 선택 위치를
    표시한다.
  - 포인터다운 시 클릭 위치가 링 안쪽 반지름보다 바깥이면 hue 드래그, 안쪽이면 삼각형(S/V)
    드래그로 모드를 한 번 정하고 드래그가 끝날 때까지 유지한다(드래그 도중 경계를 넘나들어도
    모드가 안 바뀌는 표준적인 UX).
  - HSB/RGB 탭 서브패널은 `<input type="number">` 스핀박스로 구현했다(Krita의 스핀박스와 동일한
    조작감이고, 슬라이더보다 정밀 입력에 유리). `oninput`이 즉시 `hsb`를 갱신해 휠이 실시간으로
    반응한다.
  - hex 입력 행은 기존과 동일하게 탭 조건문 바깥, 탭 패널 바로 아래에 항상 렌더링해 요구사항 5를
    자연스럽게 만족한다.
  - 스크래치 패드는 `pointerdown`~`pointermove` 동안 `lineTo`로 선을 그리는 단순한 캔버스이고,
    새로 그리는 선은 그 순간의 전경색(`hex`)을 쓰지만 이미 그려진 선의 색은 바뀌지 않는다(실제
    스크래치 패드처럼 색을 바꿔가며 이어서 칠해볼 수 있음). 우측 팔레트 컬럼을 flex-column +
    `margin-top`으로 아래로 밀어붙여 패널의 우측 하단에 위치시켰다.
- **`toolState.svelte.ts`** — `colorHistory = $state<string[]>([])`와 `addColorToHistory(hex)`를
  추가했다. 팝오버를 열고 닫을 때마다 `ColorPicker` 컴포넌트가 파괴/재생성되므로, 히스토리를
  컴포넌트 로컬 상태로 두면 팝오버를 닫을 때마다 사라진다 — 그래서 이미 존재하는 싱글톤인
  `toolState`에 두어 세션 동안 유지되게 했다. `addColorToHistory`는 정확히 같은 hex가 이미 있으면
  아무것도 하지 않고(요구사항 3), 새 색은 최신순으로 맨 앞에 추가하며 40개로 제한한다(무한정
  늘어나 팝오버를 넘치지 않도록).
  - **컬러 히스토리에 쌓는 시점은 후속 수정으로 바뀌었다 — 아래 "후속 수정" 절 참고.**

## 후속 수정 — 히스토리 반영 시점 변경 + 스크래치 패드/스크롤바 다듬기

1차 구현에서는 "컬러 피커에서 색을 확정하는 시점"(휠 드래그 종료, 숫자/hex 입력 커밋)마다 히스토리에
쌓았는데, 사용자가 정정했다: **히스토리는 실제로 그 색을 써서 그렸을 때만 쌓여야 한다** — 실제
캔버스에 드로우하거나, 스크래치 패드(미리보기)에 스트로크했을 때. 휠을 돌리거나 숫자만 바꾸고
그리지 않으면 "사용"한 게 아니므로 쌓이면 안 된다. 추가로 두 가지 다듬기 요청도 함께 반영했다:
최근 사용한 색 목록의 스크롤바 숨김, 스크래치 패드 배경을 실제 캔버스(도큐먼트) 배경색과 맞추기.

- **`brushEngine.ts`** — `createStroke$`의 `StrokeControllerOptions`에 `onStrokeEnd: (settings:
  BrushSettings) => void`를 추가했다. 스트로크마다 `exhaustMap` 클로저 안에서 한 번 캡처해 두는
  `settings`(도구/색)를 그대로 캡처해서, 기존에 타일을 플러시하던 `finalize(() => {...})` 콜백
  안에서 `flushTouchedTiles` 다음에 `onStrokeEnd(settings)`를 호출한다 — pointerup/cancel이든
  모드 이탈(Space 등으로 draw 모드를 벗어남)이든, 스트로크가 "끝나는" 모든 경로가 이미
  `finalize`로 수렴해 있어서 별도 분기를 추가할 필요가 없었다. `brushEngine.ts`는 이 콜백의
  내용(색 이력을 어디에 쌓을지)은 전혀 모른다 — `getSettings`/`getTileStore`처럼 호출부가 주입하는
  콜백 중 하나일 뿐이라, `toolState`나 컬러 히스토리 개념과 결합되지 않는다(기존 DI 스타일 유지).
- **`CanvasStage.svelte`** — `createStroke$` 호출에 `onStrokeEnd: (settings) => { if (settings.tool
  !== 'eraser') toolState.addColorToHistory(settings.color); }`를 추가했다. 지우개 스트로크는 색을
  "쓴" 게 아니므로 제외한다. `toolState`는 이미 이 컴포넌트가 다른 목적으로 임포트하고 있어서 새
  의존성이 생기지 않는다.
- **`ColorPicker.svelte`**:
  - 기존에 있던 커밋 지점(휠 `pointerup`, 숫자 입력 blur/Enter, hex 입력 blur/Enter)의
    `addColorToHistory` 호출을 전부 제거했다 — 이 입력들은 이제 순수하게 `hsb`/휠 상태만 바꾸고,
    실제로 뭔가를 그렸을 때만 히스토리에 반영된다.
  - 스크래치 패드의 `handleScratchPointerUp`에서 그 스트로크가 실제로 있었을 때만(`scratchDrawing`
    이 true였을 때만) `toolState.addColorToHistory(hex)`를 호출하도록 했다 — 클릭만 하고 아무것도
    안 그린 pointerup까지 히스토리에 잡히지 않게 하는 방어.
  - 스크래치 패드 배경을 `documentState.doc?.background.color ?? '#ffffff'`로 바인딩해 실제
    캔버스(도큐먼트) 배경색과 항상 일치하게 했다 — 하드코딩된 어두운 UI 배경(`#1e1e1e`) 대신,
    실제로 그 색이 캔버스 위에서 어떻게 보일지와 같은 배경에서 미리 볼 수 있다.
  - `.history-grid`에 `scrollbar-width: none`(Firefox) + `-ms-overflow-style: none`(레거시
    Edge/IE) + `::-webkit-scrollbar { width: 0; height: 0; }`(Chrome/Safari)를 추가해 스크롤은
    그대로 되면서 스크롤바만 시각적으로 숨겼다 — 세 규칙 모두 스크롤 기능 자체는 건드리지 않고
    스크롤바의 시각적 표현만 지우므로, "숨기지 못하면 최대한 얇게"의 폴백까지 갈 필요 없이 모든
    evergreen 브라우저에서 완전히 숨겨진다.

## 검증

- **단위 테스트**: `colorWheel.spec.ts` 신규 15개(각도 변환 왕복, 기하 계산, 무게중심좌표 왕복,
  `closestPointInTriangle`의 내부/꼭짓점/변 클램프 동작 등) — 전체 스위트 15개 파일 67개 테스트
  전부 통과. `svelte-check` 0 에러, lint(prettier+eslint) 통과, `vite build` 성공.
- **브라우저 검증**(WSL→Windows Chrome, CDP 연결, dev 서버는 사용자가 이미 실행 중이던
  `localhost:5173`을 그대로 사용): 실제 앱에서 Playwright로 다음을 확인했다.
  - HSB 탭이 기본으로 활성 상태(요구사항 1).
  - 링을 드래그해 hue를 바꾸고, 삼각형을 드래그해 saturation/value를 바꾸면 hex/HSB/RGB 필드가
    모두 실시간으로 갱신됨. RGB 탭에서 R 필드에 `10`을 입력하는 즉시(blur 전) hex가 갱신되는 것도
    확인 — 요구사항 2의 "입력하면 휠도 반응형으로 변화"가 필드→휠 방향으로도, 휠→필드 방향으로도
    성립함.
  - 링/삼각형 드래그 종료, RGB 필드 커밋마다 히스토리가 1개씩 늘어남을 확인했고, 방금 커밋한 색과
    똑같은 hex를 다시 입력해 커밋했을 때 히스토리 개수가 그대로임을 확인(요구사항 3의 중복 방지).
    히스토리 스와치를 클릭하면 그 색으로 정확히 되돌아감도 확인.
  - 스크래치 패드에 실제로 드래그해 선을 그리면 캔버스에 불투명 픽셀이 생기고, 지우기 버튼을
    누르면 다시 전부 투명해짐을 `getImageData`로 직접 확인(요구사항 4).
  - hex 입력 행이 HSB/RGB 어느 탭에서도 탭 패널 바로 아래 고정으로 보임(요구사항 5) — 스크린샷으로
    육안 확인.
  - 스크린샷으로 Krita 원본과 비교해 링/삼각형이 hue에 따라 함께 회전하고(예: hue=180으로 재선택
    시 두 썸(hue 썸/삼각형 꼭짓점)이 링 아래쪽에서 정확히 같은 각도로 일치), 채도/명도가 낮을수록
    삼각형 내 선택점이 검은 꼭짓점 쪽으로 쏠리는 것을 확인했다.
- **후속 수정 검증**(같은 방식으로 재검증): 새로 고침한 세션에서 링 드래그, RGB 필드 편집+blur,
  hex 편집+Enter를 각각 해봤지만 히스토리가 0에서 그대로임을 확인했고, 스크래치 패드에 스트로크
  하자 즉시 1개로 늘어남을 확인했다(요구사항 재확인). 서로 다른 hex 두 개(`#112233`,
  `#aabbcc`)로 각각 스크래치 패드와 실제 캔버스에 그려 히스토리가 정확히 그 두 색으로(`rgb(17, 34,
  51)`, `rgb(170, 187, 204)`) 채워짐을 확인해 실제 캔버스 드로잉이 히스토리에 반영됨을 검증했다
  (처음 시도에서는 두 스트로크에 우연히 같은 색을 써서 개수가 안 늘었는데, 중복 방지 로직이 정상
  작동한 것일 뿐 버그가 아님을 서로 다른 색으로 재확인해 확정했다). 지우개로 새 색(`#ff00ff`)을
  들고 실제 캔버스에 스트로크했을 때 히스토리 개수가 그대로임을 확인해 지우개 제외 로직도
  검증했다. 링 드래그+스크래치 스트로크를 20회 반복해 서로 다른 색 20개를 강제로 쌓은 뒤
  `.history-grid`의 `scrollHeight`(62px)가 `clientHeight`(60px)보다 커서 실제로 넘치는 상태인데도
  `offsetWidth === clientWidth`(158px, 스크롤바가 레이아웃 폭을 전혀 차지하지 않음)임을 확인해
  스크롤바가 완전히 숨겨졌음을 수치로 검증했다. 스크래치 패드 배경은
  `getComputedStyle().backgroundColor`가 기본 도큐먼트 배경색과 같은 `rgb(255, 255, 255)`임을
  확인했다.

## 알려진 한계 (의도적으로 남겨둠)

- 컬러 히스토리는 세션(페이지 새로고침 전까지) 동안만 유지된다 — 별도로 영속화(localStorage 등)
  요청은 없었고, 이 프로젝트는 캔버스 데이터만 OPFS로 영속화하고 있어 UI 상태까지 저장소를
  넓히는 건 이번 스코프 밖으로 판단했다.
- Krita 원본 다이얼로그에는 OK/Cancel 버튼이 있지만, 이 앱의 피커는 M6부터 즉시 반영(live-apply)
  방식이라 그 관례를 그대로 유지했다(선택하는 즉시 전경색이 바뀜).
